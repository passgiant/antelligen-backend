## 1. 학습한 사항

### 1.1 아키텍처 — Hexagonal / DDD 가 왜 필요한지 몸으로 느낀 시간

작업 1번(뉴스 8종목 제한 해제) 을 시작했을 때 가장 먼저 마주한 문제는 "어댑터가 다른 도메인의 use case 내부 상수를 직접 import" 하고 있다는 사실이었다.

처음엔 "import 하나 옮기면 되는 일" 이라고 생각했지만, 결국 그건 도메인 경계가 무너져 있다는 신호였다. **`TickerKeywordResolverPort` 라는 추상을 도입한 뒤** 부터는 변경의 비용이 한 도메인 안에서 끝나는 경험을 해 봤다.

> *"왜 처음부터 Port 를 두느냐"* 는 종종 과한 추상화처럼 보였는데, 막상 변경 요청이 들어왔을 때 — 그러니까 8종목 → 2,500+ 종목 확장이라는 큰 변경에서도 어댑터 한 줄만 갈아 끼우면 된다는 걸 보고서야 **"추상은 미래 자신을 위한 보험"** 이라는 말을 이해했다.

배운 것:
- **Port/Adapter** 는 의존성 역전을 위한 트릭이 아니라, 변경의 폭발 반경(blast radius) 을 한 도메인 안에 가두는 장치다.
- 도메인 레이어에서 FastAPI / SQLAlchemy / Pydantic / httpx 를 import 하지 않는다는 규칙은 **"도메인은 외부 변화에 영향받지 않아야 한다"** 라는 원칙의 자연스러운 결과물이지, 형식적인 룰이 아니다.

### 1.2 시장 추상화 — "분기는 어디서 일어나야 하는가" 의 답

US 확대 작업에서 처음에는 어댑터 안 곳곳에 `if ticker.isdigit()` 같은 조건문을 흩뿌렸다. 결과적으로 뉴스/재무/공시 어댑터가 각자 다른 방식으로 KR/US 를 판별하는 끔찍한 코드가 만들어졌다.

리뷰를 받고 `MarketRegion` 이라는 도메인 VO 와 `MarketRegionResolver` 도메인 서비스를 분리한 뒤에야 코드가 한 번에 정리됐다. **"분기의 의미를 도메인 어휘로 끌어올리면, 사용처는 단지 표현만 다르게 한다."**

배운 것:
- 같은 if 조건이 여러 어댑터에 반복되면, 그 조건은 도메인 개념일 가능성이 높다.
- enum + helper(`is_korea()`/`is_us()`) 패턴은 분기점에 의미를 부여한다 — `if region.is_us()` 는 `if ticker.isalpha()` 보다 훨씬 잘 읽힌다.

### 1.3 외부 API 의 함정

| API | 직접 부딪힌 함정 |
|-----|-----------------|
| **DART OpenAPI** | "영업(잠정)실적" 은 정규 재무제표 API 가 아니라 공시 list API 에서 제목 필터링으로 잡아야 함. 본문 숫자 추출은 HTML 파싱이 필요해 best-effort 로 시작 |
| **SEC EDGAR** | `User-Agent` 헤더가 없으면 403. 또한 ticker → CIK 매핑이 별도 endpoint(`company_tickers.json`). 그리고 `data.sec.gov` vs `www.sec.gov` 도메인이 다르다 |
| **yfinance** | 동기 라이브러리라 async 컨텍스트에서 그냥 부르면 이벤트 루프가 막힘. `asyncio.to_thread` 로 wrap 하는 패턴이 필수 |
| **SerpAPI** | `gl` / `hl` 파라미터 하나로 검색 결과의 언어/지역이 완전히 바뀐다. 같은 코드라도 locale 만 바꾸면 미국 시장 분석이 가능해진다는 게 인상적 |
| **YouTube API** | quota 가 hot-reload 한 번에 수십 unit 씩 빠진다 — 캐시 영속화의 동기 그 자체 |

배운 것:
- 외부 API 의 quirks 는 **항상 어댑터 안에서 끝내야 한다**. 도메인/응용 레이어에 외부 API 의 변덕이 새어 나오는 순간 테스트가 깨진다.
- 동기 SDK 는 `asyncio.to_thread` 로 격리하는 것이 사실상 표준 패턴이라는 것.

### 1.4 동시성 — Redis 분산 락이 처음이었다

작업 5번(On-demand 공시 + 분산 락) 이 가장 도전적이었다. 단순히 "Lock 객체 하나 만들면 되겠지" 로 시작했다가, 다음을 차례로 깨달았다:

1. **in-process Lock 은 멀티 워커/인스턴스 환경에서 무력하다.** uvicorn 워커가 4개면 락이 4개 따로 도는 거다.
2. **Redis `SET NX EX` 가 atomic single-shot** 이라 race 가 없다는 건 알았지만, 실제로 **TTL 설정** 이 왜 필수인지는 "락 보유 프로세스가 죽었을 때 deadlock" 을 시나리오로 그려보고 나서야 이해했다.
3. **Redis 자체가 다운된 경우의 정책** — 락을 못 얻으면 멈출 것인가, 락 없이 진행할 것인가? 우리는 **가용성 우선** 을 택해 락 실패 시에도 진행하도록 했다. 이건 trade-off 의식적 선택이다.
4. **락 대기자의 행동 설계** — 무한정 polling 은 안 되고, 30초 안에 DB row 가 등장하면 즉시 종료, 안 나오면 timeout 로그. 이런 "대기 측 UX" 까지가 분산 락 설계라는 걸 처음 알았다.
5. **idempotency** — `find_by_corp_code(limit=1)` 로 이미 있으면 즉시 return 하는 단순 가드 한 줄이, 동시성 문제의 절반을 미리 막아준다.

배운 것:
- 분산 락은 *atomic primitive + TTL + try/finally + graceful degrade + idempotent guard* 이 다섯 가지를 모두 갖춰야 비로소 운영 안전하다.
- "락이 있으니 괜찮다" 가 아니라 "락이 깨졌을 때 무엇이 일어나는가" 를 먼저 그려야 한다.

### 1.5 캐시 — TTL 을 정하는 것은 "정보의 본질" 을 정의하는 일

작업 4번(조건부 startup) 과 7번(사업개요 카드) 에서 4가지 다른 TTL 을 정해야 했다:

| 캐시 | 정한 TTL | 근거 |
|------|----------|------|
| 매크로 스냅샷 | 4시간 | 거시 위험은 분 단위로 안 변하지만, 하루 안엔 이벤트가 많이 일어남 |
| 회사 프로필(DART) | 1일 | 기업개황은 거의 안 변함 |
| 사업 개요(LLM) | 7일 | 비즈니스 모델은 분기 단위로도 잘 안 변함 + LLM 비용이 큼 |
| 통합 분석 | 1시간 | 시그널은 뉴스 흐름에 따라 자주 갱신되어야 함 |
| `refresh_company_list` 쿨다운 | 24시간 | DART 회사 마스터 자체의 갱신 주기 |

처음엔 "캐시 = 빠르게 하기" 라고만 생각했는데, 실제로 작업해 보니 **TTL 은 "이 정보는 얼마나 자주 변하는가" 라는 도메인 지식의 코드화** 였다. TTL 을 잘못 잡으면 사용자가 stale 데이터를 보거나, 반대로 캐시 효과가 사라진다.

배운 것:
- TTL 은 성능 파라미터가 아니라 **도메인 진실성(truth-ness)** 파라미터다.
- 같은 종목 응답이라도 "시그널 부분 = 1시간" "사업개요 부분 = 7일" 처럼 **응답 한 덩어리 안에서도 부분별 TTL 이 다를 수 있다.** 이걸 분리해서 캐시한 게 가장 자랑스러운 설계였다.

### 1.6 신뢰도(Source Tier) — 모델보다 데이터 큐레이션이 먼저

작업 3번(출처 티어 가중치) 을 진행하며 가장 크게 인식이 바뀌었다.

처음 LLM 멀티 에이전트를 접했을 때는 "LLM 을 더 좋게 만들면 답이 좋아진다" 고 막연히 믿었다. 그런데 같은 LLM 이라도 **들어가는 입력의 출처 분포** 를 가중하지 않으면 디시인사이드 글이 블룸버그 기사를 묻어버리는 결과가 나왔다.

특히 **엔터테인먼트 섹터 오버라이드** 작업에서 깨달은 게 있었다. "엔터주에서는 SNS 가 본질" 이라는 도메인 지식을 코드 한 줄(`_SECTOR_OVERRIDE`) 로 인코딩한 것 — 이게 단순한 if 문이 아니라 **"세상은 균일하지 않다"** 라는 사실을 코드에 받아들이는 일이라는 걸 알았다.

배운 것:
- AI 서비스의 신뢰도는 모델이 아니라 **소스 가중과 메타데이터 설계** 에서 절반 이상이 결정된다.
- "전 세계 모든 도메인에서 동일한 가중치" 가 더 단순해 보여도, 실제로는 **섹터별 차등이 더 정직하다.**
- 가중치 수치를 settings env 로 빼낸 것 — 이게 운영 중에 실제로 튜닝하게 만드는 진짜 활성화 장치였다.

### 1.7 부분 실패와 graceful degrade

3개 서브에이전트 병렬 호출에서 `asyncio.gather(return_exceptions=True)` 로 부분 실패를 허용하는 패턴, startup 잡 전체를 try/except 로 감싸는 패턴, Redis 다운 시 락 없이 진행하는 패턴 — 모두 **"전부 vs 전무" 를 거부하고 "부분이라도 살린다"** 라는 같은 철학에서 나왔다.

이전엔 "에러는 무조건 위로 올리는 게 정답" 이라고 배웠는데, **운영 가능한 시스템은 종종 에러를 정중하게 무력화** 한다. 다만 그 무력화가 **로그로는 모두 남아야** 한다는 것 — 이게 단순한 try/except 와의 차이다.

배운 것:
- 가용성과 정확성의 trade-off 는 의식적 선택이다 — "어느 쪽을 택할지" 에 대한 명확한 정책이 코드에 들어 있어야 한다.
- 부분 실패 허용은 게으름이 아니라 **운영 책임** 이다.

### 1.8 프론트엔드 — 백엔드 응답 설계가 결국 UX 를 만든다

사업개요 카드 작업에서, 백엔드가 같은 응답 안에 `business_overview` 라는 별도 필드를 둔 결정 — 이것 하나로 프론트엔드는 "시그널 카드와 사업개요 카드를 동시에 렌더링" 할 수 있었다. 만약 응답을 `summary` 텍스트 하나로 합쳐서 줬다면 프론트는 LLM 답변에서 사업 부분을 다시 파싱해야 했을 것이다.

`source` 필드(rag_summary / llm_only / asset_llm_only) 도 마찬가지 — 백엔드가 한 줄로 분류해 보내주니 프론트는 배지 색만 바꾸면 됐다.

배운 것:
- **응답 DTO 설계가 곧 UX 의 한계선** 이다. "백엔드가 줄 수 있는 정보 = 프론트가 보여줄 수 있는 정보".
- 풀스택 작업이 아니어도, **"이 데이터가 화면에 어떻게 그려질까" 를 백엔드 작업할 때 같이 생각하는 습관** 이 가장 중요하다는 걸 알았다.

## 2. 개인 소감

### 2.1 어려웠던 순간

가장 힘들었던 건 **Stage B(US 확대)** 였다. 뉴스/재무/공시 세 어댑터가 각각 다른 외부 API 와 붙어 있고, 각 API 마다 quirks 가 달라서 (SEC User-Agent / yfinance 동기 호출 / SerpAPI locale) 한 번에 모든 걸 "잘" 만드는 건 불가능했다. 결국 Stage B-1(뉴스+재무) → Stage B-2(SEC) 로 PR 을 쪼갠 게 옳은 선택이었다.

또 하나 힘들었던 건 **Stage D(소스 티어)** 의 가중치 숫자를 정하는 일. 1.0/0.7/0.5/0.3 이라는 수치는 "직관" 으로 정한 부분이 컸고, 머지 후 실제 데이터로 검증하기 전엔 자신이 없었다. 그래서 결국 **Feature Flag(`enable_source_tier_weighting`) 로 OFF 출시 + 가중치 env tunable** 라는 안전장치를 두 겹으로 깔았다. 실제 운영 데이터를 보고 나서 ON 하면 된다는 마음의 여유가 생겼다.

### 2.2 가장 보람 있었던 순간

`AnalyzeNewsSignalUseCase.execute("000270")` (기아) 가 처음 정상 시그널을 뱉었을 때. 이전엔 "8개 종목 외엔 빈 결과" 였던 게, Port/Adapter 를 도입한 후 **단 한 줄도 추가하지 않고도** 모든 KRX 종목이 자동 지원되는 걸 보고 가장 큰 만족을 느꼈다.

또 사업개요 카드가 프론트엔드 화면에 처음 렌더링됐을 때 — 백엔드 7일 캐시 + 병렬 fetch + RAG chunk + LLM 요약 + DTO 분리 + 프론트 카드까지의 모든 단계가 하나의 화면 위에서 협력하고 있다는 걸 봤다. **개별 작업이 모여서 사용자 가치가 되는 순간** 이라는 게 이런 거구나 싶었다.

### 2.3 협업에서 배운 것

이 프로젝트는 **단계 분리(Stage A/B/C/D)** 가 정말 잘 됐던 사례다. 한 번에 다 해버리려고 하면 PR 리뷰가 불가능했을 텐데, Stage 별로 PR 을 쪼개니 리뷰어도 작은 단위로 검증할 수 있었고, **각 Stage 가 머지된 시점에 KR 회귀가 깨지지 않는다** 는 안전장치가 자동으로 따라왔다.

그리고 PR 워크플로우(fork → branch → PR → merge commit → fork sync) 가 처음엔 번거롭게 느껴졌는데, 한 번 익숙해지니 **원본 커밋 SHA 가 보존되어 git history 에서 누가 무엇을 왜 했는지** 가 명확하게 남는다는 걸 알게 됐다. 작은 규율이 협업의 큰 비용을 줄여준다.

### 2.4 코드 외적으로 배운 것

이 프로젝트를 하면서 가장 크게 바뀐 건 **"AI 서비스의 본질이 무엇인가" 에 대한 시각** 이었다.

처음엔 "더 좋은 LLM = 더 좋은 서비스" 라고 생각했지만, 실제로 만들어 보니 **사용자 신뢰** 는
- 출처 티어로 시그널을 가중하는 메타데이터 설계,
- 캐시 TTL 로 비용을 통제하는 운영 감각,
- 부분 실패를 허용하는 견고함,
- 회사 정보 / 사업개요로 맥락을 함께 주는 UX,
- 결정 과정을 기록하는 거버넌스(LangSmith tracing)

같은 **LLM 외부의 디테일** 에서 만들어진다는 걸 깨달았다. 경쟁사 분석 문서에 적힌 *"투자 결과가 아니라 검증 가능한 의사결정 과정과 안전한 실행 구조를 제공하는 서비스가 시장 승자가 된다"* 라는 문장 — 처음엔 멋진 슬로건이라고만 생각했는데, 직접 코드로 한 줄씩 만들어보고 나서야 문장의 무게를 느꼈다.

## 3. 마무리하며 하고 싶은 말

7개의 작업이 단순한 기능 추가의 합으로 보였다면, 실제로는 그 사이를 관통하는 하나의 질문이 있었다고 생각한다.

> **"AI 가 만든 답을, 사용자는 무엇을 보고 신뢰할 수 있는가?"**

뉴스 8종목 제한을 푼 것은 *"답이 안 나오는 종목" 의 침묵을 없앴다는 의미* 이고,
US 확대는 *"한국에 갇힌 서비스" 라는 한계를 풀었다는 의미* 이며,
잠정실적 페처는 *"이미 시장에 반영된 정보만 본다" 는 한계를 깬 것* 이고,
출처 티어 가중치와 엔터 SNS 오버라이드는 *"AI 가 본 정보의 출처별 무게" 를 사용자에게 보여줄 수 있게 만든 것* 이고,
조건부 startup 과 분산 락은 *"AI 가 같은 답을 두 번 사지 않도록" 하는 운영 절약* 이고,
회사정보/사업개요 카드는 *"답을 받기 전에 회사 본질을 알고 답을 평가할 수 있게" 한 것* 이다.

각 작업은 결국 **"AI 의 답을 사용자가 검증할 수 있게 만드는 한 조각"** 이었다. 그 조각들이 모여서 단순한 시그널 산출기가 아니라 **사용자가 자기 머리로 다시 한 번 따져볼 수 있는 도구** 로 발전해 가는 걸 직접 만든 게 큰 보람이었다.

---

이 프로젝트는 **개인적으로 가장 많이 배운 6개월** 이었다.

처음 합류했을 때 도메인 / 어플리케이션 / 어댑터의 경계는 이론으로만 알고 있었고, 분산 락이나 RAG 같은 단어는 막연한 추상이었다. 하지만 7개 작업을 직접 손으로 만들고 코드 리뷰를 받고 다시 고치는 과정을 거치면서, **"왜 그렇게 해야 하는가" 의 이유** 가 생기는 경험을 했다. 이론은 코드를 직접 부숴 본 사람만이 진짜로 이해할 수 있다는 걸 새삼 느꼈다.

함께 일한 팀원분들께도 감사하다는 말을 꼭 남기고 싶다. PR 리뷰에서 받은 피드백이 없었다면 *MarketRegion 같은 추상* 이나 *섹터 오버라이드의 일반화 구조* 는 절대 떠올리지 못했을 것이다. 혼자 만든 코드와 리뷰를 거친 코드의 차이는, 같은 코드라고 부를 수 없을 만큼 컸다.

마지막으로, 이 프로젝트에서 배운 가장 중요한 한 가지를 하나만 꼽으라면 이거다:

> **"좋은 코드는 작성자가 똑똑한 게 아니라, 미래에 코드를 다시 만질 사람을 배려하는 것이다."**

Port 도입, Feature Flag, 섹터 오버라이드의 일반화, 캐시 TTL 분리, 가중치 env tunable, graceful degrade — 모든 것이 결국 **"6개월 뒤 이 코드를 만지는 사람" 을 위한 배려** 였다.

그래서 다음에 이 코드를 누군가가 이어받아 Phase 2 작업(엔터 외 섹터 확장, SEC 본문 파싱, 분산 락 ownership 토큰화) 을 한다면, **내가 받은 친절을 그대로 돌려주는 코드** 였기를 바란다.
